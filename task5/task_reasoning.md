This task belongs to the Kernel Structural Correctness category, because what is wrong in it is the address arithmetic and the launch bookkeeping of a data parallel kernel, not the arithmetic of the operation itself. There is nothing to get wrong in the maths of a gather, it only copies. The secondary category is Tensor and Memory Layout, since both defects are ultimately about a stride.

There are two independent silent defects, in two different files, and neither one can be found by reading the file it lives in.

The first is in `gatherlib/kernels/gather.py`. The kernel builds a flat offset out of two halves, `row_base = src_row.to(tl.int64) * row_pitch` and `in_row = (lane * col_pitch).to(tl.int64)`, and adds them. Both halves are 64-bit by the time they meet, and a comment says so, so the surface reading is that wide addressing is handled. The widening on the second half happens one step too late: `lane` comes from `tl.arange`, which Triton types as int32, and the column pitch is an int32 kernel argument, so the product has already wrapped before the cast sees it. This matters because it defeats the reflex repair. An agent that knows the Triton rule of thumb and blanket-casts offset arithmetic to int64 finds a cast already present on every term and changes nothing; the fix is to move one cast inside a parenthesis, which needs actual reasoning about evaluation order rather than pattern matching. That only matters when the column pitch is large, and the column pitch is only large when the table is addressed down a column rather than along a row. So the defect needs two things at once: a table big enough that a pitch times a lane index can cross 2^31, and a layout in which the pitch that gets multiplied by the lane index is the big one. A large contiguous table gathers perfectly, because its column pitch is 1. A small transposed table gathers perfectly, because its column pitch is tiny. A large transposed table loses the last 0.14 percent of every row, which the kernel's bounds clamp turns into zeros rather than an illegal access.

The second is in `gatherlib/cache.py`. Access plans, which carry the two pitches and the addressable span, are memoised per table. The key is shape, dtype, device, contiguity, the pitch of the trailing axis, and config. A stride really is in that key, so the obvious criticism, that the key ignores layout, is false: it separates a packed table from a view, and it separates a transpose or a column slice from either. What it does not separate is two unpacked views of each other's shape whose trailing axis is packed in both: `wide256[:, :128]` and `wide384[:, :128]` agree on shape, dtype, device, on being unpacked, and on a trailing pitch of 1, and disagree on the leading pitch, which is the one nobody put in the key. The second table gathered is served the first one's plan and reads the wrong rows. Grepping the file for `stride` finds a hit and looks reassuring; seeing the hole means noticing it is the wrong stride, which means going to read what `build_plan` actually consumes.

I deliberately built this version to defeat three shortcuts that killed the earlier draft of the same task.

The first shortcut was a sibling kernel that contained the correct form of the broken expression. In the earlier draft `rowsum.py` widened its loaded index to int64 before the same multiply, and that made the fix a one line diff away with no understanding required at all. In this version no other kernel multiplies a lane index by a column pitch. `row_sums` and `scatter_rows_` both declare that they need a packed trailing axis, take a ready made 64-bit row offset from the host, and walk the row with a plain add. That restriction is real and validated and it is the reason they have nothing to copy from. `gather_rows` is the only general one, so it is the only place the arithmetic exists.

The second shortcut was a correct twin sitting beside the wrong value in the same file. The earlier draft had a helper returning `shape[-1]` as a row pitch ten lines under a helper returning `stride(-2)`, which is an answer key rather than a decoy. In this version `addressing.py` and `plan.py` are both entirely correct, and the mistake is a missing element of a tuple in a third file.

The third shortcut was the symptom itself. Whole zero rows point straight at the load mask, and once a reader is looking at the mask, the only condition that can be false for a legitimate row is the one testing for a negative offset, which names the mechanism. Here the cache defect returns real values read from real neighbouring rows with no masking at all, and the width defect only zeroes a thin tail slice of an otherwise correct row.

The defects are independent. The width defect needs a large table addressed down a column, and the cache sees such a table once, so no stale plan is involved. The cache defect needs two small same-shape views, whose column pitch is 1, so no multiply overflows. Repairing either alone leaves the other's four tests failing.

The `pass_to_pass` set is built to reward wrong hypotheses. A large contiguous table works, so size alone is not it. A small transposed table works, so layout alone is not it. Every unpacked view gathers correctly on its own, so testing layouts one at a time finds nothing. Gathering from a packed table and then from an unpacked one of the same shape works, because contiguity really is in the key, so the obvious probe for state leaking between calls comes back clean. Gathering from two unpacked views of different shapes works too. There is also a decoy repair available: `validate.py` narrows row ids to int32, which looks like the cause of an overflow and is not, because the row term is already widened.

On the tests, every comparison is against something computed outside the package. The small cases compare against a gather done in plain Python over `tensor.cpu().tolist()`, so the reference goes through torch's own view handling rather than any of this code. The full size cases compare against `table[row_ids]`, against `torch.index_select`, and against a loop that fetches each row on its own. One test replaces the compiled kernel with a tripwire and asserts the gather still goes through it, because otherwise rewriting `gather_rows` as `table[row_ids]` would pass every value test without fixing anything. An autouse fixture empties the plan cache around every test, so the tests that depend on a sequence of calls are the only ones that see one.

Two environment notes for whoever runs this. The Dockerfile installs `gcc`, which is not decoration: Triton compiles a small CPython extension for its CUDA driver shim the first time any kernel is launched, and the `-runtime` base image ships neither a compiler nor the headers, so without it every test errors before a kernel runs. The build asserts on the compiler and the headers together so that surfaces at build time. And on memory: one allocation of 840000 by 2560 int8, 2.003 GiB, is shared by every full size case, with its transpose used as the second layout over the same bytes; with the CUDA context the suite needs roughly 2.5 GiB of free device memory. That cannot be lowered, because a pitch times an index has to be able to cross 2^31 for the contract to be exercised at all, and int8 is already the narrowest dtype available.

No external datasets and no pretrained models are used, so there is nothing to bundle.
