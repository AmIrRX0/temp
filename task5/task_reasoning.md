This task belongs to the Kernel Structural Correctness category, because what is wrong in it is the address arithmetic of a data parallel kernel and not the arithmetic of the operation it performs. There is nothing to check in the maths of a gather, it just copies. The secondary category is Tensor and Memory Layout, since the second defect is about deriving a pitch from the wrong property of the tensor.

I put two independent silent defects in two different files.

The first defect is in `gatherlib/kernels/gather.py`. The kernel builds the flat offset of a row as `src_row * row_pitch`. Both of those are 32 bit in the generated code, because `tl.arange` produces int32 and because Triton specialises a Python int argument as i32 whenever it fits in i32, so the product wraps once a row starts past element 2^31 of the table. The kernel does widen to 64 bit, but it widens the column term and the output offset rather than the row base, so the wrap has already happened by the time anything gets promoted. The kernel also clamps its offsets against the span of the table before loading, which is why the wrapped offset produces zeros instead of an illegal memory access. That clamp is what keeps the failure silent, and it is the same clamp the other two kernels use, so it is a habit of the package and not a marker on the broken one.

The second defect is in `gatherlib/addressing.py`, in `packed_row_strides`. When the trailing axis of the table is packed it returns `shape[-1]` as the row pitch instead of `stride(-2)`. Those two agree for a fully contiguous table, and the function is right for anything whose trailing axis is not packed, so a transposed table and a column strided table both gather correctly. It is only wrong for a table whose rows are packed but spaced further apart than their width, which is what a row step slice or a column narrowing produces. The same file holds `element_strides`, `addressable_span` and `row_offsets`, and all three of those are correct and are used by the other two kernels.

The defects are independent. Fixing only the row base leaves the row step sliced, column narrowed and column windowed cases failing. Fixing only the pitch leaves the full size table failing. Neither of them raises anything, neither changes a shape or a dtype, and both of them are invisible for a small freshly allocated table, which is why that case sits in `pass_to_pass`.

For the decoy competence I did not want a sibling kernel that could be diffed against the broken one to hand over the answer, so the two correct kernels address memory in genuinely different ways. `rowsum.py` widens the loaded row id to 64 bit and multiplies in the kernel. `scatter.py` has the row offset worked out on the host in 64 bit and only walks along the row inside the kernel. Both of them read their pitches from `element_strides`. So the package shows two working ways of doing wide addressing, and the broken kernel is a third one that looks like it belongs.

What makes this hard is that neither defect can be found by reading the file it lives in. The gather kernel is correct as written if integers are as wide as the reader assumes, and the width comes from Triton's type rules, not from anything in the repository. The pitch helper is correct for most layouts, including the non contiguous ones people reach for first, so "it breaks on views" is a wrong hypothesis that the `pass_to_pass` set actively rewards.

On the tests, every comparison is against something computed outside the package. The small cases compare against a gather done in plain Python over `tensor.cpu().tolist()`, so the reference goes through torch's own view handling and not through any of this code. The full size cases compare against `table[row_ids]`, `torch.index_select`, and a loop that fetches each row on its own. Editing the library therefore cannot make a wrong answer look right. I also added a test that replaces the compiled kernel with a tripwire and asserts the gather still goes through it, because otherwise rewriting `gather_rows` as `table[row_ids]` would pass every value test without fixing anything.

Two environment notes for whoever runs this. The first is that the Dockerfile installs `gcc`, which is not decoration: Triton compiles a small CPython extension for its CUDA driver shim the first time any kernel is launched, and the `-runtime` base image ships neither a compiler nor a way to find the Python headers, so without it every test errors out before a kernel ever runs. The build asserts on the compiler and the headers together so that failure surfaces at build time instead of at verification time.

The second is memory: the full size table is 840000 by 2560 int8, which is 2.003 GiB on the device, and it is allocated once per test session by a module scoped fixture. With the CUDA context and the small tensors on top of it the suite needs roughly 2.5 GiB of free device memory. There is no way to lower that, since the table has to span more than 2^31 elements for the contract to be exercised at all, and int8 is already the narrowest dtype available.

No external datasets and no pretrained models are used, so there is nothing to bundle.
